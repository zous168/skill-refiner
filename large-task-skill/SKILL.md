# GoalExecutor 目标执行器

GoalExecutor 是复合任务的进度执行器，适用领域不限；领域名称、任务看起来“可以拆步骤”或最终答复较长，都不是启用理由。只在下方门槛满足时启动，避免给能直接完成的小任务增加快照、Viewer 和调度负担。

GoalExecutor 用轻量快照追踪目标、验收标准、待办和证据，并在宿主支持本地文件与浏览器时打开只读 Viewer。主Agent是唯一调度者和共享进度状态写入者；子Agent只执行被分派的子任务并回传证据。按宿主实际能力委派；Skill 指令不能创建不存在的调度器、保证上下文隔离或强制执行。子Agent的返回内容可能进入主Agent上下文，归档和自动续跑也取决于宿主。不要把这些能力描述成保证。

软件 Epic / Gate 是可选叠加档，用户没点名「按 LT / 写代码仓库」就不要建 `LT-*.json`。字段与可选档见 [reference.md](reference.md)。调用样例见 [examples.md](examples.md)。

## 何时启用

用户明确要求使用 GoalExecutor、按 LT 执行时，始终启用。未明确要求时，只有以下条件**全部满足**才自动启用：

1. 任务包含至少三个有实质产出的步骤，并形成两个或更多相互依赖的阶段；单个长时间运行、需要定期检查点的工作也满足此项。
2. 预计会跨多个对话轮次，或必须等待阶段交接/长时间执行；能在当前轮直接交付的任务不满足此项。
3. 保存验收标准、证据和进度对避免遗漏有明显帮助。

普通问答、简单查询、短文案、单点代码修复、轻量分析，以及可在一轮内完成的小任务，直接按普通方式处理；不能为了达到门槛而人为拆分。工具调用多、答复较长或属于某个特定领域，本身都不足以触发。判断不确定时默认不启用。若用户后来扩大范围且满足门槛，从剩余工作开始初始化即可。

- 「继续」只有在用户明确指向 GoalExecutor 或当前任务时才算续做请求；不能单凭这个词启动旧任务。
- 未完成快照只是恢复线索，不是恢复授权。先比对当前请求与快照中的目标；无关请求照常处理，快照保持不变。若存在多条可能的续做任务，列出目标并询问用户。
- 用户要求「一个 Agent 做」时，不委派。可以用主Agent维护的轻量检查点继续工作。

## 启动前检查

开始前记录用户目标原文、约束和可验收结果，并检查宿主是否提供所需能力：子Agent调用、持久化目录、文件交付、并行调度。只有能力真实可用且用户没有要求单Agent时才委派。不可用时，主Agent可直接完成且能可靠交付就继续；否则说明具体限制并标记 `blocked`。不要假装已经隔离、归档或运行了不存在的调度工具。

发送、发布、部署、删除或修改外部系统等副作用，仍须遵守用户授权和宿主规则；GoalExecutor 的自动续做约定不能替代授权。

## 角色与职责

1. **主Agent（调度者）**
    - 常驻上下文：用户目标原文、约束、验收标准、轻量快照。
    - 负责任务拆分、目标对齐、状态更新、结果交付和完成判断。
    - 不加载与当前检查无关的长素材；需要核验用户交付物时，可读取最小必要内容或委派校验。
2. **子Agent（可选执行者）**
    - 每次调用只接收一项明确子任务、对应目标标准、范围和必要素材。
    - 宿主可能提供独立上下文，但主Agent仍可能收到较长返回；按实际工具行为控制回传量。
    - 只执行收到的子任务，不得再派发或委派工作，也不得直接修改共享快照、runtime、current 指针或 Viewer 数据；若任务超出范围，返回缺口或 `blocked`。
    - 返回状态、已覆盖的目标标准、证据引用和未解决缺口。只有宿主支持持久化时才声称已归档。
3. **产物归档层（逻辑层，契约定义，不需要数据库代码）**
    - 宿主支持文件写入时，将完整成品保存到任务归档并分配 `art_xxx`；否则按宿主支持方式返回成品。
    - ref 是定位符，不等于用户已收到交付物。完成时必须提供用户可访问的路径、链接或实际答复。

长流程子 Skill（如 `skill-refiner`）的进度归属、run 指针和精确恢复规则见
[reference.md](reference.md) 的「长流程子 Skill 进度交接」。主Agent仍负责总目标、当前子任务和面向用户的进度；子 Skill 只负责内部阶段状态与证据。Viewer 是共享进度的只读呈现层，不负责调度。

## 目标与验收标准

初始化时把目标拆成少量可观察的验收标准，使用稳定 ID（如 `G01`）。标准必须来自用户目标和约束；不要把实现偏好伪装成业务要求。每个待办都必须引用至少一个 `goal_ref`，并说明 `done_when`。没有目标关联的工作应删除、标为可选，或作为范围变更交用户确认。

用户后来明确改变目标时，保留最初的 `global_goal` 原文，在 `goal_changes` 记录用户提出的变更和生效时间。按变更补充标准；若旧标准因此不再适用，将其标为 `superseded` 并引用该变更，不得静默删除或改写。

每次派发前检查：「这项工作对应哪个 G 标准？完成证据是什么？是否仍在用户要求的范围内？」收包后更新标准状态和证据引用。子任务完成不代表目标标准已验证。

## 标准快照

```json
{
  "task_id": "GE-ling-20261027-110831-a3f2",
  "global_goal": "调研三家竞品的定价与功能差异，并写销售话术",
  "constraints": ["只依据公开信息", "禁止编造报价"],
  "success_criteria": [
    {"id": "G01", "criterion": "提供三家竞品的可核验对照", "status": "pending", "evidence_ref": null},
    {"id": "G02", "criterion": "销售话术符合约束且可交付", "status": "pending", "evidence_ref": null}
  ],
  "goal_changes": [],
  "todo_specs": [
    {"subtask_id": "A01", "title": "圈定竞品与信息源", "goal_refs": ["G01"], "done_when": "确认三家竞品并列出可核验的公开来源；未知价格明确标注"},
    {"subtask_id": "A02", "title": "整理对照表", "goal_refs": ["G01"], "done_when": "三家竞品功能与定价逐项有来源或明确标为未知"},
    {"subtask_id": "A03", "title": "撰写话术", "goal_refs": ["G02"], "done_when": "产出一页销售话术且每项事实符合约束"},
    {"subtask_id": "A04", "title": "核验交付", "goal_refs": ["G01", "G02"], "done_when": "核验事实与约束，并确认对照表和话术可访问"}
  ],
  "current_subtask": "A01：圈定竞品与信息源",
  "done": [],
  "pending": ["A01：圈定竞品与信息源 [G01]", "A02：整理对照表 [G01]", "A03：撰写话术 [G02]", "A04：核验交付 [G01,G02]"],
  "status": "continue",
  "block_reason": null,
  "artifacts_ref": {},
  "child_agent_calls": [],
  "next_instruct": null
}
```

- `success_criteria`：少量可验收结果；仅在有证据时设为 `verified`。
- `todo_specs`：为全部待办保存短标题、`goal_refs` 和具体 `done_when`；每条 `pending` 必须恰好对应一个 `subtask_id`。完成待办时从 `todo_specs` 移除。派发时将对应规格复制到调用对象，不能临时改写标准来迎合结果。
- `child_agent_calls`：当前未完成的调用；回执按 `subtask_id` 匹配，清空已收包调用。
- 规则：done/pending只存短摘要、目标 ID 和引用，**禁止嵌入长文本内容**。
- `artifacts_ref` 只记 `{ "art_001": "一句话标题" }`，禁止贴全文
- `next_instruct` 只用于宿主确实支持自动续跑的情形；不能强迫宿主调用或代替用户授权。
- `tasks`（可选）：Viewer 的层级展示投影，不替代 `todo_specs`、`pending` 或验收证据。每项只有唯一非空 `id`、`parentId`、`title`、`status`；根节点的 `parentId` 为空，其他节点指向现存父节点，不得形成环。可执行叶节点的 `id` 与对应 `todo_specs.subtask_id` 相同；仅分组节点可使用独立 ID。`status` 仅用 `pending`、`in_progress`、`done`、`blocked`，由主Agent随待办进度同步；验收证据仍以快照标准和 `todo_specs.done_when` 为准。完成项保留在树上，只更新状态。通用任务树不写后端、前端、对接、单测、E2E 等软件分层。

## Viewer 可视化同步

GoalExecutor 进入多步执行后，在宿主提供本地持久化和浏览器能力时，为当前任务打开 Viewer。单任务页面读取 `.tasks/snapshots/{task_id}.json` 与 `.tasks/runtime/{task_id}.json`。任务层级来自快照可选字段 `tasks`：按 `parentId` 显示任意层级；可执行叶节点 ID 对应 `todo_specs.subtask_id`，分组节点使用独立 ID。`current_subtask` 以待办 ID 加中文冒号开头时，Viewer 精确标记该待办。Viewer 只读；进度和验收以快照的 `todo_specs`、`pending` 与验收标准为准。

### 单任务视图

1. 初始化快照后准备 Viewer：页面要能按 `parentId` 展开多层任务。`.tasks/` 里已有的旧页如果做不到，不要复用；保留原文件，改用本 Skill 随附的 [viewer.html](viewer.html)，复制为 `.tasks/goalexecutor-viewer.html`。没有旧页时，复制为 `.tasks/viewer.html`。
2. 用可观察的前台会话在 `.tasks/` 启动本地静态服务器：`python -m http.server 8765 --bind 127.0.0.1`。若端口已占用，确认现有服务指向当前 `.tasks/` 后复用；否则选择空闲端口。不要终止未知进程或启动不可观察的 detached 服务。
3. 使用宿主的浏览器打开 `http://127.0.0.1:<端口>/<viewer文件名>?task_id=<task_id>`。Viewer 每 3 秒读取当前快照和 runtime；状态更新以磁盘上的 JSON 为准。页头“项目总览”入口可切换到项目视图。
4. 只有主Agent可以写快照、runtime、`current-{actor}.json` 和 Viewer 所读的共享计划数据。子Agent按 `file_scope` 写自己的交付物，完成后回传证据，由主Agent更新状态。
5. 若宿主无法持久化文件、启动可观察的本地服务器或打开浏览器，说明缺少哪项能力，继续用宿主支持的进度格式；不要声称 Viewer 已打开或实时同步。

### 跨项目总览

项目总览使用宿主或用户明确登记的本地项目目录，不扫描磁盘。项目清单 `.tasks/project-sources.json` 是本机配置，包含 `projects[]`，每项为 `{ "id", "name", "path" }`；不要把含本地绝对路径的清单提交到仓库。主Agent仅在有权限的项目清单工具可用时据此更新登记项，否则沿用用户提供或已登记的项目。

运行 [update_project_dashboard.py](scripts/update_project_dashboard.py) 读取清单中每个 `<path>/.tasks/snapshots/GE-*.json`，生成 `.tasks/project-dashboard.json`。汇总保留项目名/路径、目标摘要、状态、验收计数、待办计数、更新时间和可选 `tasks` 树，并为只读详情页生成字段白名单投影及有限的 runtime 计数；不复制 prompt、日志或产物正文。打开 `?view=projects` 查看项目及其 GoalExecutor 目标任务；总览仅展示至少有一个目标任务的项目，空项目不显示。点击目标名称可打开该任务详情，详情页的「项目总览」入口可返回。跨项目详情从汇总投影读取，不直接加载登记项目中的任意文件。不带 `task_id` 或 `actor` 时也默认进入总览。新增项目或快照状态变化后，主Agent重新生成该文件；Viewer 每 3 秒读取汇总投影，但该文件不是执行状态源。

首次计划、阶段切换、收到回执、预算接近上限、阻塞和完成后，主Agent更新快照；单任务 Viewer 会在下一次轮询时反映变化。若启用跨项目总览，主Agent在更新快照后重生成 `project-dashboard.json`。子Agent心跳可以进入 runtime，但不自动增加 GoalExecutor 的检查点计数。

## 强制运行规则

1. 全局基础规则
    - pending数组不为空，**严禁标记status=complete**
    - 每个待办先对齐一个或多个验收标准；不要为了保持流水线而执行无目标关联的工作
    - 预估token接近上限，优先输出快照、标记continue，停止扩写
    - 软熔断：最多20个主Agent状态检查点；连续两个完成的检查点没有新证据、标准状态或任务进度 → `blocked`。达到第20个检查点后，若任务仍未完成，在开始任何新工作前标记 `blocked` 并报告剩余项。指纹包括标准、范围变更、待办规格、done/pending、未完成调用及总状态，不包括时间戳和轮数。等待中的子Agent不计停滞轮次。
    - 不允许修改global_goal顶层目标
2. 子Agent调用隔离规则
    - 委派是可选能力；服从用户选择和宿主限制。
    - 子Agent回执至少包含：执行状态、`goal_refs`、证据引用、交付方式、摘要和未解决缺口。
    - 对复杂或高风险交付，安排独立校验；简单交付由主Agent按明确标准轻量核验。
    - 不声称主Agent永远看不到子Agent输出，也不把文件存在当作内容正确的证据。
3. 按需召回规则
    - 后续工作依赖历史细节时，向有权限的执行者提供最小必要素材或 ref。
    - 控制上下文体积，但不能为了保持隔离而阻止最终核验或用户交付。

## 标准流转

1. **初始化**：确认当前请求指向新任务还是某条续做任务；写入用户目标原文、约束、验收标准和目标关联待办。
2. **派发或执行**：宿主支持且用户允许时，按 `goal_refs`、`done_when` 和最小必要素材派发；否则由主Agent执行可完成部分。
3. **收包与对齐**：按 `subtask_id` 收回执，记录证据、缺口和标准状态。必要时独立校验。只在有新进展或证据时标记对应项完成。
4. **检查点**：每次主Agent持久化一次有意义状态更新，`round` 加一。初始化拆分、收到结果、处理用户澄清/恢复各计一轮；仅等待运行中的调用不计数。停滞指纹至少包含验收标准状态及证据、范围变更、待办规格、done、pending、未完成调用和全局状态；排除时间戳与轮数。
5. **完成**：只有 pending 全部清空、所有仍有效的必需标准均已验证（被用户明确替代的标准标为 `superseded`）、没有未解决阻塞且用户可访问最终交付物时，才能设 `complete`。
6. **阻塞/恢复**：记录具体原因和等待的用户信息。用户提供所需信息后沿用原 `task_id`，保留目标原文，把阻塞项恢复为待办并重新核验；不得只因旧快照存在就自动恢复。

`continue` 表示仍有工作；如果宿主不支持自动续跑，就报告检查点并在当前回合可行时继续，不要声称已自调用。`complete` / `blocked` 不触发自动续跑。

## 推理分配

- 推理等级由宿主支持范围决定；不要假设存在 `low`、`high`、`max`，也不要声称已设置宿主不支持的等级。
- 若宿主允许单独设置子Agent等级，简单抽取可用较低等级，复杂创作或精细推理可用较高等级。

宿主不支持设置推理等级时，使用其默认配置，不声称已按某个等级运行。

## 可选调度指令

下面内容是普通任务指令模板。Skill 不能修改宿主的 system prompt；只在宿主支持时作为任务上下文使用：

```
你启用 GoalExecutor 目标执行器。
你是调度主Agent。遵守用户指定的执行方式和当前宿主实际提供的能力。
规则：
1. 保留global_goal原文，维护少量 success_criteria；每个待办必须引用目标标准并有 done_when。
2. 维护轻量快照，done、pending只放短摘要、目标ID和证据引用。
3. 只有用户允许且宿主实际支持委派时才用 child_agent_calls；不得承诺上下文隔离。
4. 收到结果后核对 goal_refs、证据和缺口；子任务完成不自动代表目标标准已验证。
5. 只要pending非空或必需标准未验证，status禁止设为complete。
6. 最多20个已完成主Agent检查点；等待中的调用不算停滞。连续两个检查点无新进展或证据时标记 `blocked`。第20个检查点后若仍有工作，在开始下一项前停止并报告剩余项。
7. 用户明确改变范围时保留原goal，追加 goal_changes；不得静默改写。
8. 宿主支持结构化快照时使用约定JSON，否则用清晰的等价格式。自动续跑只在宿主确实支持时使用。
```

对用户的进度说明保持简短：当前子任务名、status、已覆盖标准、证据引用和阻塞。不要无谓复述长素材；最终答复必须让用户取得所需交付物。

## 根任务编号（多人防冲突）

仓库里多人同时开 GoalExecutor 时，禁止用全局自增或纯时间戳当根编号。根 ID 必须带执行人，且落盘前检查所有可能冲突的快照、runtime、归档和旧路径。

1. `actor`：`git config user.email` 的 `@` 前一段 → 否则 `user.name` → 否则环境变量 `USERNAME` / `USER` → `anon`。只留 `[a-z0-9]`，小写，最长 16。
2. 根编号：`GE-{actor}-{yyyyMMdd}-{HHmmss}-{rand4}`，例如 `GE-ling-20261027-110831-a3f2`。`rand4` 为 4 位小写十六进制。生成后检查 `.tasks/snapshots/{task_id}.json`、`.tasks/runtime/{task_id}.json`、`.tasks/artifacts/{task_id}/` 和旧路径 `.tasks/{task_id}.json`；任一存在就重抽 `rand4`（最多 5 次）。生成成功后只读，不复用。
3. 每人一份指针：`.tasks/current-{actor}.json` → `{ "task_id": "GE-..." }`。禁止写公共 `snapshot.json` / `current.json`。
4. 产物按根任务分目录：`.tasks/artifacts/{task_id}/art_001.md`。`art_xxx` 只在该 `task_id` 内递增，跨人允许都从 `art_001` 起。
5. 旧的无 actor 编号（`GE-20261027-110400`）只读兼容，新建必须带 actor。软件档额外的 `LT-{actor}-{NNN}` 见 [reference.md](reference.md)，默认不建。

同一条根任务要两人接力：沿用已有 `task_id`，不要再发新号。各开各的任务则各发各的号。

## Cursor 落地

| 角色 | 本会话对应 |
|------|------------|
| 主Agent | 当前对话。按宿主能力维护快照、runtime 和交付物 |
| 子Agent | 宿主提供且用户允许时调用；不能假设每次都是全新上下文 |
| 归档 | 宿主支持持久化时用 `.tasks/artifacts/{task_id}/art_xxx.md`（或同名 `.json`） |

1. 默认串行派发。仅当宿主明确支持并行、任务彼此独立且文件/数据范围不重叠时，才可一次启动多个调用；软件档还须遵守 L3 的开发→测试→Gate 串行门禁。不能并行时按队列逐项执行，并在 `child_agent_calls` 中只保留当前实际派发项。
2. 每个 prompt 必须带 `goal_refs`、`done_when`、范围、回执契约和必要素材，见 [reference.md](reference.md)。
3. 子Agent按宿主能力保存或直接交付完整成品，并返回 `status`、`goal_refs`、`evidence_refs`、`delivery_mode`、`art_ref`、摘要和缺口。文件存在不代表内容正确。
4. 快照只存摘要、目标ID和引用。主Agent可读取核验最终用户交付所需的最小内容，也可委派独立校验；不得为了减小上下文而遗漏最终交付。
5. 续做先确认当前请求指向该任务，再读本 actor 的 current 与对应快照。按需访问归档，遵守访问权限和最小必要原则。
6. `task_id` 空则按「根任务编号」生成。`art_xxx` 在该 `task_id` 目录内三位递增，不复用。

pending 默认写成 `A01：短名`。只有用户明确要按 LT / 软件仓库交付时，才叠加三层任务库，写成 `A01：LT-{actor}-001.01.01 开发 · 标题`。

## 调用示例

> 使用GoalExecutor，顶层目标：调研三家竞品的定价与功能差异，整理对照表，并写一份给销售用的一页纸话术；约束：只依据公开信息，禁止编造报价

其他领域同一套契约，只换 goal / constraints。更多样例见 [examples.md](examples.md)。

## 边界与取舍

收益：目标、待办和证据之间可追溯；快照保持轻量；宿主具备相应能力时可委派和续跑。

局限（软契约，无程序兜底）：模型可能偏离快照约定；子Agent输出可能进入主Agent上下文；文件归档、自动续跑和20轮熔断都不是 Skill 本身提供的硬保证。超长素材要按宿主能力分片；无法验证的项目不得标记完成。

扩展（未实现，不要提前做）：子Agent内置小 GoalExecutor；产物版本标记；pending 优先级标签。
